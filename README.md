# ユーザー勤怠・体調管理システム (self_care_automation)

ユーザーが日々の勤怠や体調（睡眠時間、服薬状況等）を記録し、施設スタッフが一元管理・サポートするための、Djangoで構築されたWebアプリケーションです。
実務を見据え、**「N+1問題の解消」によるSQLの最適化**、環境変数を用いた**「開発環境（SQLite3）と本番環境（Neon / PostgreSQL）の完全分離」**、さらにデプロイ時の**「インテリジェントなゲストデータ自動クリーンアップ検知」**など、バックエンドおよびインフラ自動化（DevOps）の品質に徹底的にこだわって開発しました。

---

## 💻 プロジェクト概要

このシステムは、利用者が自身の体調変化（セルフケア）を可視化して把握できるようにしつつ、施設スタッフがリアルタイムで状況を確認し、適切な声かけやデータ分析を行えるように設計されています。

### 👥 主なターゲット・利用シーン
- **利用者 (CLIENT / user_role=1)**: カレンダーから日々の勤怠・体調・服薬状況・作業内容を入力し、過去のグラフから自己管理に役立てる。
- **スタッフ (STAFF / user_role=2)**: 利用者一覧から当日の状況を俯瞰し、不足情報のチェックや個別フィードバック（コメント・入退室時間の補正）を行う。土曜開所日の管理も担当。
- **管理者 (ADMIN / user_role=3)**: ユーザーの新規作成・編集・削除など、セキュアな本人認証フローを経たマスタ管理を行う。

### ⚠️ 無料プランに関する注意点
1. **初期ロードのスリープについて**
   Renderの無料プランの仕様により、15分間以上アクセスがない場合、Webサーバーが自動的にスリープ状態になります。そのため、上記URLへの初回アクセス時、サーバーの起動に **50秒〜1分程度** の時間がかかる場合があります（コンテナ起動後は高速に動作します）。
2. **データベースの永続化について**
   本番データベースにはサーバーレスの **Neon (Postgres)** を使用しているため、サーバーコンテナがスリープ・再起動した場合でも、登録したユーザーデータや勤怠レコードは安全に永続化されます。

## ✨ 主な機能一覧

### 1. ユーザーロール（権限）の3段階制御
- **利用者**: 自身のホーム画面、勤怠・体調入力、過去の推移グラフ表示、コメント履歴の閲覧。
- **スタッフ**: 利用者一覧（ページネーション・進捗未入力バッジ）、スタッフコメント入力、土曜開所日の登録・削除管理。
- **管理者**: 全ユーザーの管理メニューへのアクセス、管理者用パスワード認証を挟んだユーザーのCRUD（作成・編集・削除）フロー。

### 2. カレンダー・勤怠入力
- 日曜日の自動入力制限や、登録された土曜開所日のみ入力可能とする営業日判定ロジック。
- 在宅（リモート）出勤時と通常出勤時で、バリデーションロジックを動的に切り替え（例：在宅時はスタッフの入退室時刻を必須化、通常時は自身の入退出時間を必須化）。

### 3. Matplotlibによる体調・睡眠の可視化
- 過去30日間の「睡眠時間の推移（折れ線グラフ）」および「体調の推移（〇✕△プロット）」を、登録完了画面や詳細画面にBase64エンコードのインライン画像としてシームレスにレンダリング。
- 過去3ヶ月の「月間平均睡眠時間（バーチャート）」を自動集計して描画。

## 🚀 システムエンジニアとしてのこだわり・実装の工夫

### ⚡ 1. N+1問題の解消とSQL最適化
当初、利用者一覧画面（`UserListView`）で全ユーザーの日々の勤怠状況やホーム画面IDを取得する際、ループ内で都度SQLが発行される「N+1問題」が発生していました。
これを解決するため、**対象日のデータを`__in`句を使って事前に一括取得（バルク取得）し、メモリ上で辞書（マッピング）化して結合するアプローチ**へリファクタリングしました。
これにより、ユーザー数が増加した場合でもDB負荷を大幅に削減し、画面のレスポンス速度を高速化させています。特に本番環境である外部のNeon (PostgreSQL) とのネットワーク越しの通信回数を最小限に抑える設計を強く意識しました。

### ⚙️ 2. 本番（PostgreSQL）と開発（SQLite3）の設定完全分離
運用の利便性と保守性を両立させるため、設定ファイルを本番用の `settings.py` とローカル開発用の `settings_dev.py` に完全分割しました。
開発環境側では外部サービス（NeonやCloudinary）への接続依存を一切遮断し、軽量な組み込みのSQLite3で完全にクローズドかつ高速に動作するよう設計しています。また、`manage.py` 内部で動作環境を自動感知し、ローカル起動時は自動的に `settings_dev.py` が取り込まれる親切設計を施しています。

### 🛡️ 3. デプロイ時のゲストデータ自動自動クリーンアップ感知（DevOps）
第三者が動作検証のために作成した一時的なテストアカウントや関連レコードが本番環境のデータベース内に溢れるのを防ぐため、カスタム管理コマンド（`clean_guest_users`）を自作しました。
Renderへのデプロイ（ビルド）が走る際、スクリプト（`build.sh`）内で**「ホワイトリスト以外の新規ユーザーが作成されているか」を事前に自動感知**し、存在する場合にのみクリーンアップ処理を自動キックするインテリジェントなCI/CDパイプラインを構築しています。

### 🔒 4. セキュアな管理者認証フロー
管理者がユーザー情報の編集や削除を行う際、誤操作や離席時の不正操作を防ぐため、**「管理者パスワードによる再認証 (AdminScreenView)」および「対象ユーザーのメールアドレス確認 (UserAuthView)」という二重の認証ステップ**（確認画面を含むセクションフロー）を実装しました。

## 🔧 環境構築・起動方法

開発環境（ローカルPC）で一からシステムを動作確認するための手順です。Windows環境（コマンドプロンプト/PowerShell）およびMacの両方に完全対応しています。

1. **リポジトリのクローンとプロジェクトへの移動**
   ```bash
   git clone https://github.com/ooo20050808/dc_tennoji_self_care_manager
   cd dc_tennoji_self_care_manager/self_care_automation
   ```

2. **仮想環境の作成と有効化**
   ```bash
   python -m venv venv  # コマンドエラーが出る場合は「py -m venv venv」
   
   # 【環境に合わせ、いずれか1つのコマンドを実行して有効化】
   # Windows (コマンドプロンプト) の場合:
   venv\Scripts\activate
   # Windows (PowerShell) の場合:
   ./venv/Scripts/activate
   # Mac / Linux の場合:
   source venv/bin/activate
   ```

3. **パッケージのインストール**
   ```bash
   pip install -r requirements.txt
   ```

4. **データベースの初期化（マイグレーション）と管理者ユーザー作成**
   ※ローカル環境では、自動的に開発用の軽量なSQLite3（`db.sqlite3`）が自動生成されます。
   ```bash
   python manage.py makemigrations --settings=self_care_automation.settings_dev
   python manage.py migrate --settings=self_care_automation.settings_dev
   python manage.py createsuperuser --settings=self_care_automation.settings_dev
   ```

5. **開発用サーバーの起動**
   ```bash
   python manage.py runserver --settings=self_care_automation.settings_dev
   ```
   起動成功後、ブラウザで **`http://127.0.0`** にアクセスし、手順4で作成したアカウントでログインしてください。外部スタイルシート（`style.css`）が適用された、モダンなUIのログイン画面が表示されます。
